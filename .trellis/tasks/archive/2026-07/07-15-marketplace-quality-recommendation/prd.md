# 市场质量与推荐

## Goal

在 v4 插件市场上交付可解释、可复算、抗简单刷量的“已上架 / 优质 / 精选”三级质量体系，以及“精选 / 分类热门 / 近期优质”三类非个性化推荐，让用户能更快找到可信插件，让作者能明确知道等级依据并对异常结果申诉。

## User Value

- 用户可以区分“通过基础审核”“由数据证明表现稳定”“由平台人工推荐”三种不同信号。
- 用户看到的市场排序对所有人使用同一套公开规则，不依赖隐式画像或付费竞价。
- 作者可以看到指标口径、不达标原因和最近一次计算时间，并通过现有工单渠道申诉。
- 平台运营可以人工精选、处理异常信号和重新计算，但不能绕过上架、安全、策略或兼容性门禁。

## Confirmed Baseline

- v4 市场事实源是 `PluginPackage -> PluginRelease -> MarketplaceListing`；只有活动 listing 的精确 `currentReleaseId` 可以出现在市场。
- 当前 v4 市场目录只有按 listing 更新时间返回的扁平列表，尚无权威分类、质量等级或推荐区。
- `MarketplaceListing` 保留了从旧市场迁移来的安装和评分聚合字段，但旧 `/api/marketplace/*` 评分与安装接口已经返回 `client_upgrade_required`，这些聚合不能继续充当 v4 质量事实源。
- 当前购买权益按团队和 package 唯一，下载与运行授权绑定精确 release；这些事实可以作为可信消费信号。
- 当前本机安装账本属于设备，不属于服务端。服务端不能把目录曝光、重复下载或客户端自报计数直接当成独立用户量。
- 桌面端已有一套本地关键词分类，但它不是跨桌面、Web、服务端一致的市场契约，不能直接驱动服务端“分类热门”。
- 平台已有 v4 审核/下架、安全策略、审计日志、团队状态和帮助反馈工单，可复用于硬门禁、人工操作记录与作者申诉。

## Requirements

### R1. 三级质量语义

- 市场只展示三个等级：`已上架`、`优质`、`精选`。
- `已上架` 表示 package 活动、listing 活动、精确 current release 已发布且通过市场与当前安全政策检查；它不表示平台对使用效果的额外背书。
- `优质` 由版本化公开规则自动计算，不能由管理员直接强制授予。
- `精选` 由平台人工授予，必须记录操作者、公开理由、开始时间、可选结束时间和稳定排序；精选到期后自动回落到其自动等级。
- 等级优先级为 `精选 > 优质 > 已上架`。精选不能绕过上架、安全、团队策略、权益、版本兼容或平台下架；任一硬门禁失败时立即停止展示，而不是继续保留精选曝光。
- current release 指针每次生效都必须保存 `currentReleaseActivatedAt` 和不可变切换历史；新 release（包括切回旧 release）从本次 pointer 生效时间重新经过至少 7 天和足够运行样本的观察，不能用 release 发布时间、listing 更新时间或旧快照代替。
- 连续资格必须有独立 epoch 事实：listing 下架/重上架或任一审核、安全、release hard gate 失效后恢复时重置 listingEligibleSince 与 releaseEligibleSince；仅 current pointer 变化时保留未中断的 listing epoch但重置 release epoch。不能用当前 status 或 updatedAt 反推连续 14/7 天。

### R2. 优质规则 v1

一个 listing 只有同时满足以下条件才进入 `优质`：

- listing 连续活动至少 14 天，当前已审核 release 连续可用至少 7 天。
- 最近 30 天有至少 20 个合格活跃团队。活跃团队指非作者团队、状态正常，并至少完成一次平台可关联到精确 release 的成功运行；同一团队无论成员数和运行次数只计一次。
- 最近 30 天至少有 50 次可观察终态运行，插件归因失败率不高于 2%。用户取消、权限/权益拒绝、余额不足、平台级故障和明确的上游平台故障不计为插件失败。
- 至少有 10 个合格团队评分，按“一团队一票”的当前有效评分计算，平均分不低于 4.3/5。
- 对付费插件，退款指标只使用明确标记 `SETTLEMENT_V2`、位于最近 90 天且已经走完 7 天可退款窗的 cohort；至少 10 笔可判定订单且获批退款率不高于 5%。尚无 settlement-v2 持久化激活事实、窗口内存在 legacy/未知版本订单，或 cohort 存在尚未决议的 `REFUND_REQUESTED` 时，退款项必须为 `data_unavailable` 并阻止晋级，不能把它们当作 0 次退款；免费插件该项为“不适用”。
- 最近 90 天没有确认的刷量处置，且当前没有未解决的高危/严重安全问题、平台下架或审核阻断。
- 任一指标样本不足时结果是“数据不足”，不能按 0% 故障或 0% 退款自动通过。

### R3. 指标可信度与反刷

- 安装、运行、评分、购买、退款、故障和安全信号必须绑定 package、精确 release、团队和服务端可验证的事件身份，并支持去重和重放。
- 本机运行可以由宿主上报，但必须先取得服务端签发且绑定用户、团队、package、release 与时效的运行会话；每个会话只能接受一个终态。
- 云端、工作流和跨插件运行直接使用平台执行记录，不允许调用方提交任意 package ID 或任意成功次数。
- 同一团队只贡献一个活跃团队和一个当前评分；作者团队、被退款权益、停用团队、平台测试数据和明确标记的异常样本不进入公开质量指标。
- 当前评分行只做最新投影；每次创建/修改都追加包含 score/revision/recordedAt/source 的不可变 RatingRevision。快照按 factWatermark 选择每团队最后一版 revision，并按 watermark 时刻的 entitlement/成功运行事实判断资格，禁止读取后来覆盖的当前 score。
- 重复下载、重装、刷新页面、同团队多成员评分或重复提交终态不能增加质量样本。
- 系统执行最小异常检查：短时突增、同一用户控制的多团队集中贡献、评分与真实使用不匹配。命中异常时暂停自动晋级并进入人工复核，不直接公开个人或团队身份。
- 反刷只影响质量与推荐，不删除原始订单、权益、评分或运行记录；排除理由、操作者和恢复动作必须审计。

### R4. 分类与非个性化推荐

- 市场分类使用服务端权威固定枚举：AI 与助手、效率与办公、开发工具、数据与可视化、图像与多媒体、文件与存储、网络与接口、系统与监控、其他。
- 新提交市场的 listing 必须选择一个分类；现有 listing 使用确定性迁移结果或“其他”，作者和有权平台管理员可以修改，修改保留审计。
- 市场首页只提供三类推荐：人工精选、分类热门、近期优质。
- `精选` 区按有效人工精选排序展示。
- `分类热门` 在所选分类内按最近 30 天合格活跃团队数降序，其次按首次成功安装团队数、有效评分和稳定 package ID 排序；不按付费金额、平台分成或广告出价排序。
- `近期优质` 只包含最近 30 天首次或重新达到优质的 listing，按达到时间倒序展示。
- 推荐结果对所有用户使用同一全局顺序。团队策略、发行状态、权益与兼容性只负责过滤不可用项，不生成个人画像或改变其余项目的相对顺序。
- 推荐区为空时展示真实空状态，不用未达标插件或旧版 legacy 计数填充。

### R5. 透明度、人工操作与申诉

- 平台向所有用户公开等级定义、优质 v1 阈值、计算窗口、最后计算时间和推荐排序字段。
- 市场列表与详情展示等级、评分数量、最近更新时间及足以解释等级的摘要；作者视图展示精确指标、数据不足项、被排除原因和对应计算快照。
- 平台管理员可以设置/取消精选、暂停/恢复某 listing 的自动优质资格、补充处置原因并触发重算；所有操作必须留审计。
- 平台管理员不能把未满足规则的 listing 手工标记为 `优质`，也不能让精选绕过硬门禁。
- 作者可以针对当前质量快照发起一次活动申诉。申诉复用现有帮助反馈工单及其回复/状态能力，不建设第二套对话系统。
- 申诉本身不自动改变等级。管理员处理后如需改变结果，必须先修正错误数据、解除有理由的暂停或重新计算，并留下独立审计。

### R6. 跨端与运行保障

- contract、collab-api、桌面端、后续 Web 插件中心和 collab-admin 使用同一分类、等级、指标摘要和推荐区契约，不在各端重新计算等级或排序。
- 指标计算必须产生不可变快照并记录规则版本；同一事实集和规则版本重复计算应得到同一结果。
- 快照身份必须同时保存 `factWatermark` 与单调 `computationRevision`；每日/手工调度的 `jobKey` 只负责计算请求幂等，不能充当快照唯一键。listing 只允许 CAS 指向当前 pointer 下按 watermark/revision 排序最新的成功快照，迟到旧计算不能覆盖新结果。
- 质量实现依赖 M2 dark `MarketplaceCommerceFactsAdapter`，而不直接在可选 schema 上拼 ORM 查询；只有 `settlementV2ActivatedAt` 缺失或 writerMode 为未激活的 LEGACY/DRAINING 时返回 DATA_UNAVAILABLE。V2 激活后的 PAUSED 仅暂停新购买，adapter 仍按 watermark 还原既有 cohort；真实读取/一致性故障令本次 job 失败并保留上一成功快照，不能伪装成 DATA_UNAVAILABLE。
- 每日计算失败不得清空上一份完整快照或把插件降为错误状态；系统保留上一份成功结果并暴露计算延迟。
- 市场查询必须分页或有明确区块上限，不能为首页一次读取全部 listing、完整运行事件或完整评分。
- 质量与推荐故障不得影响已购插件的下载、精确 release 运行授权或本机安装列表。

## Acceptance Criteria

- [ ] 市场只出现“已上架 / 优质 / 精选”三个等级，且三个等级的用户文案与本 PRD 一致。
- [ ] 活动 listing 的精确 current release 通过审核和安全门禁后至少为“已上架”；下架、撤回、封禁或政策失败后不会因旧快照或精选继续展示。
- [ ] 使用同一组事实重跑优质 v1 计算得到相同快照结果，快照包含规则版本、窗口、分子、分母、通过项和未通过原因。
- [ ] 优质判定覆盖 14/7 天观察期、20 个活跃团队、50 次运行、2% 故障率、10 个评分、4.3 平均分、付费插件 10 笔成熟订单和 5% 退款率边界。
- [ ] current release 首次启用、升级和切回旧 release 都写 `currentReleaseActivatedAt`/历史；7 天观察严格从对应 pointer 生效 instant 起算。
- [ ] listing 下架重上架、安全/审核/release hard gate 阻断后恢复都会关闭旧 eligibility epoch并重置连续 14/7 天；单纯 current pointer 切换只重置 release epoch，所有转移有不可变历史和 revision CAS。
- [ ] 任何 hard gate 可见状态与 eligibility epoch/gate digest 在同一数据库事务提交；恢复后目录只有在 digest/revision 对齐时才读取新 epoch，否则 fail-close 为隐藏/LISTED，不能在 projector lag 中短暂复用旧 QUALITY。
- [ ] 0 次运行、0 个评分或付费插件 0 笔成熟订单显示“数据不足”，不会因分母为零晋级。
- [ ] settlement-v2 尚无持久化激活事实、90 天窗口内有 legacy/未知版本订单或成熟 cohort 有 `REFUND_REQUESTED` 时，退款指标显示 `data_unavailable` 且不能晋级；这些订单不会被解释为真实 0 退款。
- [ ] 同团队 100 次运行、10 个成员评分、重复下载或重复终态只贡献一个团队/一个评分/一个运行终态对应的合法计数。
- [ ] 评分在 factWatermark 后修改不会改变该 watermark 的重算；evaluator 从 append-only RatingRevision 还原每团队最后一版，并按 watermark 时刻资格纳入/排除。
- [ ] 作者团队、停用团队、退款后失效权益和明确测试数据不进入公开质量指标。
- [ ] 本机运行终态只能提交给未过期、绑定精确 release 的服务端运行会话；重复、跨团队、跨 release 或任意伪造会话被拒绝并审计。
- [ ] 云端/工作流运行直接从平台执行事实生成指标，不能由插件请求体自行指定成功事件。
- [ ] 短时突增或多团队控制关系异常会暂停自动晋级并进入人工复核；清除异常后可从原始事实重新计算。
- [ ] 管理员可以创建带理由和时间范围的精选；到期回落到自动等级，并发设置/取消不会留下两个活动精选状态。
- [ ] 管理员无法手工强制授予“优质”，但可以带理由暂停/恢复自动资格和触发重算。
- [ ] 市场首页稳定提供人工精选、分类热门、近期优质三个区块；分类热门严格按公开字段排序且稳定处理并列。
- [ ] 相同市场状态下，不同用户获得相同推荐顺序；只允许团队策略、兼容性、权益和发行门禁过滤不可用项。
- [ ] 分类由服务端契约返回，桌面与 Web 不再因本地关键词版本不同而把同一 package 分到不同分类。
- [ ] 用户可以查看优质规则和等级解释；作者可以查看精确快照与不达标原因。
- [ ] 同一 package 和快照只能有一个活动申诉；申诉进入现有工单中心，处理结果不会在无独立数据修正/重算审计时直接改等级。
- [ ] 每日计算中断时目录继续使用上一份成功快照并显示延迟，已购下载与运行授权不受影响。
- [ ] snapshot unique identity 包含 factWatermark/computationRevision；相同 jobKey 重试复用原成功结果，不同重算可创建新 revision，较旧/迟到 job 无法把 listing pointer 回退到旧成功快照。
- [ ] 只部署 dark commerce schema 且 writerMode=LEGACY 时质量模块可 typecheck/运行并返回 refund DATA_UNAVAILABLE；不直接引用尚未部署的 M3-only ORM 字段。
- [ ] settlement-v2 已激活后 writerMode=PAUSED 仍可计算 watermark 前既有 V2 cohort；adapter/数据库故障导致 job 失败并保留上一成功 snapshot，而非提交 DATA_UNAVAILABLE 并批量回落付费 listing。
- [ ] legacy `Plugin.installCount/rating*` 和已停用旧市场接口不会被当作新的 v4 优质事实源。
- [ ] contract、collab-api、desktop、collab-admin 的相关类型检查、单元测试、构建与关键端到端场景通过。

## Dependencies

- 依赖现有 v4 package/release/listing/entitlement、精确 release 运行门禁、审计与团队状态。
- 与跨插件、工作流和 cloud 子任务共享平台运行终态，但质量任务只消费其正式执行事实，不定义第二套执行器。
- 与市场结算子任务通过 `settlementVersion`、`refundableUntil`、订单状态及 PURCHASED/REFUNDED 事实集成；只有 settlement-v2 可退款 cohort 可产生可用退款率，legacy/未启用/待审核状态显式不可用。
- Web 插件中心子任务消费本任务的市场发现契约；本任务不单独建设第二套 Web 市场后端。

## Constraints

- 规则和排序必须可解释、可复算、可测试；首版不使用黑盒模型。
- 不采集与质量判定无关的内容、通讯录或跨站行为，不对外暴露团队/用户级原始事件。
- 保持现有 v4 目录、购买、权益、下载和本机安装兼容；新增字段只能扩展现有响应，不能静默重命名现有 v4 字段。
- 本任务处于规划阶段，用户统一评审前不启动实现。

## Out of Scope

- 个性化推荐、协同过滤、用户画像、A/B 排序实验和机器学习排序。
- 广告竞价、付费置顶、销量分成加权、优惠券、联盟返利或评分奖励。
- 自动理解评论文本、通用内容审核模型或公开反作弊风控细节。
- 真实支付、提现、税务、结算与营销活动实现；这些属于市场结算子任务。
- 将旧 `Plugin` 市场路由重新启用，或把设备本地安装账本迁移为服务端安装事实源。
